# Frontend Knowledge Transfer (KT) - Secure Chat API

## 1. Project Overview
This project is an enterprise-grade secure chat application backend built using **Node.js, Express, TypeScript, and Sequelize (MySQL)**. It focuses heavily on security, utilizing short-lived access tokens, active session device tracking, and end-to-end payload signing for chat modules.

The primary responsibilities of the frontend will be:
1. Managing complex authentication flows (OTPs, session tracking).
2. Implementing an RSA-SHA256 signature generation script for the Chat module.
3. Maintaining a persistent WebSocket connection (Socket.IO) for real-time messaging.

---

## 2. Global Response Structure
Every single REST API endpoint in this system (success or error) returns a standardized JSON structure. 

**Success Response:**
```json
{
    "success": true,
    "code": 3006,
    "message": "Login successful.",
    "data": { ... }
}
```

**Error Response:**
```json
{
    "success": false,
    "error_code": 1001,
    "error": "email must be a valid email"
}
```
*Note: Any non-200 HTTP status code will have `success: false`. Always rely on `error_code` for programmatic error handling, and `error` for the human-readable UI message.*

## 3. Authentication & Session Flow
The backend uses a dual-token architecture paired with database-backed session tracking.

### The Flow:
1. **Registration:** `POST /api/user/register`
   - Returns a `unique_id` (e.g., `U-0000001`).
   - Dispatches an OTP to the user's email.
2. **Email Verification:** `POST /api/user/email-verify`
   - User submits the 6-digit OTP. 
3. **Login:** `POST /api/user/login`
   - Expects `email`, `password`, and a `deviceId` (unique string generated by the frontend app).
   - Returns a short-lived `access_token` (JWT) and sets a long-lived `refresh_token`.
4. **Session Maintenance:** `POST /api/user/refresh`
   - When the `access_token` expires, call this endpoint to seamlessly get a new one without forcing the user to log in again.
5. **Session Management:**
   - Because sessions are stored in the DB, users can see active devices (`GET /api/user/session`) and log out remotely (`POST /api/user/logout-all`).

## 4. The Cryptographic Handshake (CRITICAL)
For maximum security, the **Conversations/Messaging** endpoints are heavily protected. A standard Bearer token is **not enough**. The frontend must cryptographically sign all chat requests.

### Step A: Fetch Credentials
Upon successful login, call `GET /api/user/get-credentials`. 
The server will return:
- `api_key`
- `salt_key`
- `private_key` (an RSA Private Key).

*The frontend MUST securely store these keys locally (e.g., SecureStore on React Native, or IndexedDB on Web).*

### Step B: Signing Requests
For any request made to the `/api/user/conversations/*` routes, the frontend must attach three specific headers:
1. `x-api-key`: The API key fetched above.
2. `x-api-timestamp`: The current UNIX timestamp in seconds.
3. `x-api-signature`: The generated signature.

**How to generate the `x-api-signature` on the Frontend:**
1. Concatenate the endpoint path, the JSON stringified body (or `{}` if empty), the timestamp, and the `salt_key`.
   *Example:* `String to Hash = "/direct" + '{"userId": "123"}' + "1698765432" + "salt123"`
2. Generate an HMAC-SHA256 hash of that string using the `salt_key`.
3. Sign that resulting HMAC using the RSA `private_key` (via a standard RSA-SHA256 crypto library).
4. Base64 encode the final output. That is your `x-api-signature`.

*(If the timestamp drifts by more than 5 minutes from the server time, the request will be rejected to prevent Replay Attacks).*

## 5. Real-Time Chat (Socket.IO)
While you send messages via the REST API, you **receive** messages and typing indicators via WebSocket.

### Connection
Use the standard `socket.io-client` package. Pass the JWT `access_token` in the connection handshake.
```javascript
import { io } from "socket.io-client";

const socket = io("https://your-api-url.com", {
    auth: { token: "Bearer YOUR_ACCESS_TOKEN" }
});
```

### Key Events to Listen For:
- `message:new` - Fired when a new message is received.
- `typing:start` - Fired when a user in the active conversation starts typing.
- `typing:stop` - Fired when a user stops typing.

### Key Events to Emit:
- `join_conversation` - Tell the server you have opened a specific chat UI (pass the `conversationId`).
- `typing:start` / `typing:stop` - Emit these when the user interacts with the keyboard.

## 6. Lookups Module
For onboarding and profile screens, use the `/api/user/lookups` endpoints.
- `GET /api/user/lookups/mobile-country-codes`: Use this to populate the mobile country code dropdown (contains the actual `isdCode`).
- `GET /api/user/lookups/countries`: Use this to populate standard country dropdowns (returns standard `alpha3Code` values).
- *Both endpoints return full image URLs for the country flags, dynamically generated by the backend server.*
